What this XML sitemap generator does and when sitemaps help crawling


This utility converts a newline-separated list of webpage addresses into a standards-compliant sitemap.xml document formatted to the Sitemaps.org 0.9 XML Schema. As it builds your file inside the browser tab, it deduplicates repeated URLs (keeping first occurrences), escapes reserved XML characters, validates whether every address uses https://, detects accidental mixed hostnames, measures exact uncompressed file size in kilobytes, and provides one-click copy and application/xml file download.


Search engines primarily discover webpages by following internal links from your homepage, hubs, and navigation menus. However, link discovery alone frequently leaves blind spots—especially on newly launched domains with very few external backlinks, large e-commerce catalogs with thousands of product URLs buried four or more clicks deep, editorial archives updated infrequently, and static websites containing orphan landing pages or campaign pages excluded from the main navigation bar. Submitting a clean XML sitemap gives Googlebot, Bingbot, and YandexBot an explicit canonical inventory so crawlers locate newly published and materially updated pages promptly without guessing your directory structure.


Think of an XML sitemap as an architectural blueprint rather than a shortcut around poor site structure. While a clean sitemap speeds up discovery and gives you rich coverage diagnostics inside Google Search Console, pages that remain completely unlinked internally still struggle to accumulate internal link authority and rank competitively. The strongest technical setup pairs a clear internal navigation hierarchy with an accurate, noise-free sitemap.xml that mirrors your canonical URL inventory.


All processing executes 100% locally in your browser without sending your site inventory to any server. If you press the optional Get AI insight button, only anonymous summary counts (URL total, duplicate count, chosen priority and frequency, whether lastmod is enabled, HTTPS status, mixed-host flag, and kilobyte size) leave the tab; your actual URLs and domain name remain completely private.



How the Sitemaps.org 0.9 protocol and UTF-8 escaping work


Published jointly by major search engines under the Sitemaps.org 0.9 standard and governed by W3C XML 1.0 syntax rules, every valid sitemap document shares a strict parent-child hierarchy. The document must use UTF-8 character encoding, begin with the XML declaration, declare the official http://www.sitemaps.org/schemas/sitemap/0.9 namespace on the root <urlset> element, and wrap each webpage inside its own <url> block.





Because sitemaps are parsed by strict XML parsers before a crawler inspects any webpage, a single unescaped ampersand inside a query string (such as ?category=books&page=2 written raw instead of ?category=books&amp;page=2) causes Google Search Console and Bing Webmaster Tools to fail the entire file with an XML syntax error. Under XML 1.0, five characters inside text elements must be entity-escaped whenever they appear inside a URL: ampersand (&amp;), single quote (&apos;), double quote (&quot;), less-than (&lt;), and greater-than (&gt;).


International websites with accented characters, non-Latin scripts (such as Arabic, French accents, Swahili loanwords with diacritics, or Cyrillic slugs), or spaces in URL paths must follow strict URI encoding alongside UTF-8 file saving. Every URL inside <loc> must follow RFC 3986 URI escaping rules—converting UTF-8 characters into percent-encoded sequences (for example, encoding a space as %20) rather than pasting unencoded Unicode whitespace—while saving the actual sitemap.xml file in UTF-8 without a stray Windows-1252 conversion or leading Byte Order Mark (BOM) before the <?xml declaration.

Last modified dates (<lastmod>) without crawl-trust penalties


The <lastmod> element is the highest-leverage optional tag in your sitemap—provided your workflow treats it truthfully. According to Google Search Central's documentation, crawlers evaluate over time whether a domain's <lastmod> timestamps genuinely match observed changes to page text, structured data, or key media. When a CMS plugin or static build script blindly stamps all 500 URLs with today's date during a header CSS tweak, copyright year swap, or nightly container rebuild, search crawlers discover unchanged pages beneath brand-new dates and stop prioritizing your <lastmod> values across the whole domain.


Conversely, when <lastmod> advances strictly when a guide receives revised statistics, updated screenshots, corrected calculators, or new FAQs, Googlebot and Bingbot can re-allocate crawl capacity directly toward those freshly updated pages rather than wasting requests re-verifying untouched archive posts.


Follow four practical rules whenever enabling timestamps:


    

  • Use YYYY-MM-DD cleanly: While W3C Datetime permits full timestamps like 2026-11-14T14:30:00+00:00, date-only YYYY-MM-DD avoids timezone off-by-one confusion and matches editorial "Last Updated" stamps cleanly.
    • 

  • Single story of truth across three layers: Whenever you substantially edit a guide, synchronize the visible on-page updated date, the Schema.org JSON-LD dateModified field, and that single URL's <lastmod> in sitemap.xml—while leaving untouched URLs at their genuine older dates.
    • 

  • Use the generator's global checkbox selectively: Check Include today's date as lastmod on initial site launch or when migrating/republishing every listed page simultaneously. For incremental updates to a multi-page site, generate the clean XML skeleton with the box unchecked, then edit <lastmod> on the specific pages modified.
    • 

  • Understand what counts as a meaningful update: Reordering a sidebar widget or tweaking ad script placement is not a meaningful page edit. Reserve <lastmod> bumps for new paragraphs, corrected formulas, updated product pricing/availability, new media assets, or added FAQ answers.
    • 




URL hygiene audit: what to include vs exclude from sitemap.xml


A sitemap's power is diluted by noise. Including broken URLs, non-canonical duplicates, or blocked paths does not crash Googlebot, but it wastes crawl capacity and triggers noisy warnings in Google Search Console's Sitemaps and Page Indexing reports.





    

  • Never mix www and apex hostnames or http:// and https://: If your canonical site lives at https://afriwidget.com/, every single <loc> must start with https://afriwidget.com/. Listing https://www.afriwidget.com/about forces crawlers to waste a hop resolving your 301 redirect and flags the URL as non-canonical in indexing diagnostics.
    • 

  • Match trailing-slash policy consistently: Decide once whether URLs omit trailing slashes (/about), include them (/about/), or end in .html, and ensure your <loc> strings match your <link rel="canonical"> tags character for character. Listing /pricing/ in your sitemap while your canonical tag declares /pricing sends contradictory signals that slow canonical selection.
    • 

  • Exclude redirects, noindex, and robots.txt blocks: Never list URLs carrying <meta name="robots" content="noindex">, 301/302 redirect paths, 404 pages, utility login/cart endpoints, or paths matched by Disallow: in your Robots.txt Generator configuration.
    • 

  • Skip thin parameter and pagination noise: Internal site search queries (/search?q=tax), sort orders (?sort=price_asc), session tokens, and empty tag archives dilute crawl efficiency. Include only substantive, unique landing pages and indexable editorial content.
    • 



Specialized sitemaps: Image, Video, Google News, and Hreflang Extensions


While a standard sitemap.xml handles HTML pages cleanly for most small and mid-sized sites, search engines also support XML namespace extensions inside <urlset> when rich media or multilingual localization plays a central role in organic traffic:


    

  • Multilingual xhtml:link (hreflang) sitemaps: Global sites publishing equivalent English, French, Swahili, or Arabic versions can declare language-region pairs cleanly in XML using the xmlns:xhtml="http://www.w3.org/1999/xhtml" namespace on <urlset>—keeping HTML page templates lighter while ensuring every language variant cross-references itself and all alternates bi-directionally.
    • 

  • Image & Video extensions: Sites serving high-value visual catalogs, infographics loaded asynchronously via JavaScript, or embedded tutorials can append <image:image> or <video:video> metadata tags to help search crawlers discover media assets that might otherwise sit behind lazy-loaders.
    • 

  • Google News sitemaps: Time-sensitive newsrooms publishing breaking coverage can maintain a separate rolling News sitemap covering only articles published within the past 48 hours using the xmlns:news schema, keeping breaking URLs clearly separated from the main evergreen archive sitemap.
    • 



<!-- Example multilingual hreflang entry inside <urlset xmlns:xhtml="http://www.w3.org/1999/xhtml"> -->
<url>
  <loc>https://example.com/en/pricing</loc>
  <xhtml:link rel="alternate" hreflang="en" href="https://example.com/en/pricing" />
  <xhtml:link rel="alternate" hreflang="fr" href="https://example.com/fr/tarifs" />
  <lastmod>2026-11-14</lastmod>
</url>



Scaling past 50,000 URLs with sitemap index files and gzip


If your publishing archive, job board, or storefront expands past 50,000 URLs or 50 MB uncompressed (often reached earlier on sites with verbose multi-line formatting), split URLs cleanly across logically grouped child sitemaps and unite them beneath a root <sitemapindex> document.





A valid sitemap index uses the <sitemapindex> root tag (with the exact same http://www.sitemaps.org/schemas/sitemap/0.9 namespace) and lists each child sitemap inside a <sitemap> element:


<?xml version="1.0" encoding="UTF-8"?>
<sitemapindex xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <sitemap>
    <loc>https://example.com/sitemap-pages.xml</loc>
    <lastmod>2026-11-14</lastmod>
  </sitemap>
  <sitemap>
    <loc>https://example.com/sitemap-articles.xml</loc>
    <lastmod>2026-11-14</lastmod>
  </sitemap>
</sitemapindex>


Note two strict protocol limits: sitemap index files cannot nest inside other sitemap index files, and each child sitemap can optionally be compressed with gzip (for example sitemap-articles.xml.gz) to save bandwidth while remaining under the 50 MB uncompressed ceiling.

  4. Add the Sitemap: directive to robots.txt: Append a single line Sitemap: https://yourdomain.com/sitemap.xml at the bottom of your root robots file using our Robots.txt Generator. You may list multiple Sitemap: lines—even pointing to a sitemap index—inside one robots.txt.

That single filtered view tells you whether Google is indexing pages cleanly or flagging submitted URLs with warnings such as "Duplicate without user-selected canonical", "Crawled - currently not indexed", or "Excluded by 'noindex' tag"—allowing you to prune weak or misconfigured URLs before they accumulate.

How to interpret Google Search Console sitemap statuses


After uploading and submitting sitemap.xml, Search Console reports both an upload status and a discovered URL count. Knowing what each message means saves wasted troubleshooting:


    

  • "Success" with 0 discovered URLs: Search Console parsed valid XML, but none of the listed URLs have been crawled or associated with the sitemap yet, or the submitted file is a newly added index whose child sitemaps are still queued. Check back in 48 to 72 hours and test one URL directly with URL Inspection.
    • 

  • "Indexed, not submitted in sitemap": Google found and indexed valid pages via internal or external links that were omitted from your sitemap.xml. Either add those missing canonical pages to your sitemap list or inspect whether duplicate parameterized variants need canonical consolidation.
    • 

  • "Couldn't fetch": Either the server returned HTTP 404/5xx, a firewall blocked Googlebot's fetch of /sitemap.xml, or Search Console has not completed its initial background pull yet (very common for the first few hours after submitting a brand-new URL). Verify HTTP 200 and plain XML headers with curl first.
    • 




Where this tool stops and technical scope disclaimer


This client-side generator formats, escapes, and deduplicates the list of URLs you enter according to the Sitemaps.org 0.9 specification. Because it runs strictly inside your browser without making server-side HTTP requests, it does not crawl your live website, check whether your pasted URLs return 200 OK instead of 301 or 404, inspect HTML <link rel="canonical"> tags, read X-Robots-Tag headers, or verify your live server's robots.txt exclusions. Always inspect Search Console's Sitemaps report and Page Indexing dashboard after uploading to verify live server behavior.


Similarly, this tool builds a single <urlset> sitemap per run rather than generating a multi-file <sitemapindex> wrapper or automatic CMS build webhook. Sites exceeding 50,000 indexable URLs should generate separate section files and combine their public URLs using the <sitemapindex> structure documented in Section 6.

Frequently asked questions
What is an XML sitemap?
An XML sitemap is a plain text file in XML format that lists the important URLs on a website so that search engines can discover them more easily. It follows the Sitemap Protocol 0.9 published at sitemaps.org and is understood by Google, Bing, Yandex, and most other major crawlers. The file is usually named sitemap.xml and placed at the root of the domain, where crawlers look for it automatically. A sitemap does not guarantee indexing, but it does help a search engine find new and updated pages faster than link discovery alone.
Where should I upload sitemap.xml?
Place the file at the root of the exact host, for example https://example.com/sitemap.xml. A file inside a subfolder does not describe the whole domain, and a file on a subdomain does not cover the main site. Each host needs its own sitemap. Once the file is uploaded, confirm it loads publicly with a 200 response and the correct XML content type before submitting the URL in Google Search Console and Bing Webmaster Tools.
Does a sitemap guarantee that Google will index my pages?
No. A sitemap is a discovery aid, not a ranking or indexing instruction. Google still decides which pages to crawl and which to index based on content quality, duplication, canonical signals, and its own evaluation of the page. A well-formed sitemap can help Google find pages faster and can help diagnose problems when pages are missing from search results, but it cannot force a page into the index.
What does the priority field actually do?
The priority field is a relative hint between 0.0 and 1.0 that describes how important a URL is compared with the other URLs on the same site. It does not affect how your page ranks against pages on other sites, and Google has said publicly that it largely ignores the value. Setting every page to 1.0 removes the signal entirely, because relative importance only carries meaning when the values differ. Use priority sparingly and honestly.
What does changefreq actually do?
The changefreq field is a hint about how often a page is likely to change. Valid values are always, hourly, daily, weekly, monthly, yearly, and never. Google has stated that it largely ignores changefreq and prefers to detect changes on its own by comparing page content. Bing and Yandex are more likely to use it. If you do include the field, set it to a value that reflects reality rather than an optimistic best case.
Should I include lastmod in my sitemap?
Yes, when the date is accurate. A lastmod that reflects a real content change is one of the most useful signals in a sitemap, because it helps a search engine decide whether a recrawl is worthwhile. A lastmod that updates automatically on every server build, or that reflects the date the file was generated rather than the date the page changed, is worse than no lastmod at all. Use the real modification date of the content, and keep it consistent with any datePublished or dateModified fields in your structured data.
How many URLs can one sitemap contain?
A single sitemap file may contain up to 50,000 URLs and must be no larger than 50 megabytes uncompressed. If your site exceeds either limit, split the URLs across multiple sitemap files and reference them from a sitemap index file. Each sitemap in the index is listed with its own location and, optionally, its last modification date. A sitemap index can itself contain up to 50,000 sitemap entries.
Should I include pages that are blocked by robots.txt or that have a noindex tag?
No. A sitemap should only list the preferred, indexable URLs on the site. Including a page that is blocked by robots.txt or marked noindex creates a contradiction that wastes crawl resources and can confuse diagnosis in the webmaster tools. Remove redirected URLs, error pages, staging paths, internal search results, and login pages from the list. Keep only the URLs you want a search engine to crawl and consider for indexing.
Is my list of URLs sent to a server?
No. The generator runs entirely inside your browser, and the XML file is assembled locally from the URLs you paste. Nothing is transmitted anywhere, and nothing is stored. If you press the AI insight button, only an anonymous summary of the URL count, the duplicate count, the default priority, the default change frequency, and whether last-mod dates were included is sent to a small serverless function that runs once and then stops. The actual URLs are never included.
How often should I regenerate the sitemap?
Regenerate the sitemap whenever the set of indexable URLs changes, such as when pages are added, removed, renamed, or given a new canonical address. On a small static site that may be once a month; on an active blog it may be after every publication. The sitemap does not need to be regenerated just because a page's wording changed, as long as the lastmod date reflects the real modification and the URL set is unchanged.
Do I need to escape characters like ampersands (&) inside sitemap URLs?
Yes. Because sitemap.xml is strict XML 1.0, any ampersand (&), apostrophe ('), quote ("), less-than (<), or greater-than (>) character inside a <loc> URL must be XML-escaped (for example & becomes &amp;). Unescaped query parameters cause XML parsers in Google Search Console to reject the entire sitemap with a parse error. This generator escapes all five characters automatically.
What is the difference between an XML sitemap and an HTML sitemap?
An XML sitemap (sitemap.xml) is a machine-readable UTF-8 file formatted strictly for search engine crawlers such as Googlebot and Bingbot. An HTML sitemap is an ordinary human-facing webpage with categorized links that helps visitors navigate your site and distributes internal PageRank. Most content sites benefit from keeping both clean and synchronized.
How should I reference sitemap.xml inside robots.txt?
Add a single absolute line at the bottom of your root robots.txt file: Sitemap: https://example.com/sitemap.xml. Always use the full protocol and canonical hostname, never a relative path. Search crawlers read this directive automatically across hosts even before you submit the URL in webmaster tools.
How do I fix a Google Search Console 'Couldn't fetch' or 'Blocked by robots.txt' sitemap error?
First confirm the live sitemap URL returns HTTP 200 OK (not a 404, 5xx, login redirect, or soft-HTML block) with an application/xml or text/xml header. If Search Console reports URLs blocked by robots.txt, audit every <loc> entry against your root robots.txt rules and remove any disallowed administrative, filter, or search URLs from the sitemap.
